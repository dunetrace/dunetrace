## Commands

```bash
# Start the full stack
docker compose up -d
docker compose build --no-cache   # force rebuild

# Run all tests (no Docker required)
make test

# Run one service's tests
make test-api        # services/api/tests/
make test-detector   # services/detector/tests/
make test-explainer  # services/explainer/tests/
make test-alerts     # services/alerts/tests/
make test-ingest     # services/ingest/tests/

# Run a single test file
PYTHONPATH=packages/sdk-py:services/explainer:services/api \
  python -m unittest tests.test_native_explain -v   # from services/api/

# SDK tests (fully offline, no backend needed)
cd packages/sdk-py && python -m unittest discover -s tests -v

# TypeScript SDK tests (fully offline, no backend needed)
cd packages/sdk-ts && npm test

# End-to-end autofix test (requires running stack + an LLM key in .env)
python scripts/test_autofix.py --agent-id my-agent --signal-id 42

# Rebuild and restart a single service after code changes
docker compose up --build api -d

# Restart detector after editing detectors.yml
docker compose restart detector
```

**PYTHONPATH pattern** — every service needs its own path prefix because they share packages:
- Ingest: `packages/schemas-py:services/ingest` — deliberately does **not** include `packages/sdk-py`; ingest_svc has no runtime dependency on the SDK package
- API: `packages/sdk-py:services/explainer:services/api`
- Detector: `packages/sdk-py:services/detector`
- Alerts: `packages/sdk-py:services/explainer:services/alerts`

`packages/schemas-py` (`dunetrace-schemas`) holds the canonical Pydantic v2 wire-format models (`AgentEventSchema`, `FailureSignalSchema`) used at the ingest boundary. It depends only on `pydantic` — not on `dunetrace` (the SDK), which guarantees zero required dependencies of its own. Enum parity between the two is enforced by `packages/schemas-py/tests/test_sdk_parity.py`, not by an import relationship.

## Architecture

Five services communicate only through a shared Postgres database. No message broker.

```
SDK → Ingest API (:8001) → Postgres
                               ├─ Detector Worker (polls every 5s)
                               ├─ Alerts Worker   (polls every 10s)
                               └─ Customer API (:8002) ← Dashboard (:3000)
```

**Ingest API** (`services/ingest/`) — entry point for all SDK traffic. Returns 202 before writing to DB. Zero detection logic.

**Detector Worker** (`services/detector/`) — the only process that runs detection. Polls for completed/stalled runs, reconstructs `RunState` from events, runs 16 Tier 1 detectors (plus extracts PROMPT_INJECTION_SIGNAL from events), writes `failure_signals`. After each run it also upserts `issues` rows (auto-resolves after 5 consecutive clean runs) and evaluates any active/shadow custom detectors. `PROMPT_INJECTION_SIGNAL` is special — the SDK detects it on raw input before hashing and embeds evidence in the `run.started` payload; the worker extracts it from there. All built-in signals are written with `shadow=TRUE` unless listed in `LIVE_DETECTORS` in `services/detector/detector_svc/db.py`. Custom detector signals use `shadow=TRUE` when status is `shadow`, `shadow=FALSE` when `active`. Horizontally scalable by `agent_id` hash bucket: set `SHARD_COUNT=N` and run N replicas each with `SHARD_INDEX=0..N-1`; default `SHARD_COUNT=1` means no sharding.

**Explainer** (`services/explainer/`) — a library (not a process), imported by both alerts worker and customer API. Returns `Explanation` objects from deterministic string templates in <1ms. No LLM calls. The LLM-backed root cause analysis lives in `services/api/api_svc/native_explain.py`, not here.

**Alerts Worker** (`services/alerts/`) — polls for unalerted live signals, calls explainer, formats for Slack/webhook, delivers with exponential backoff retry, marks `alerted=TRUE` after delivery. Also manages weekly digest via `digest_log` table.

**Customer API** (`services/api/`) — FastAPI service. `AUTH_MODE=dev` skips all auth (used in local Docker). Writes to the `fixes` table and the `custom_detectors` / `custom_detector_results` tables.

**Custom Detector Translator** (`services/api/api_svc/custom_detector_translator.py`) — translates plain-English descriptions to structured detector configs via LLM (Claude Haiku). `SUPPORTED_METRICS` dict constrains the 12 detectable metadata metrics; `CONTENT_FIELDS`/`CONTENT_OPERATORS` constrain content conditions (text inspection against `tool_args`/`tool_error`/`llm_output`/`input_text` via `contains`/`starts_with`/`ends_with`/`equals`/`length_gt`/`length_lt`/`regex_matches`) — see `docs/detectors.md`. A condition is either metric-shaped or field-shaped; both kinds AND together in one detector. `evaluate_custom_detector()` (`services/detector/detector_svc/custom_detector.py`) enforces a per-detector wall-clock evaluation budget (default 10ms, `detectors.yml`'s `custom_detectors:` section) and a ReDoS-safe timeout on `regex_matches` (via the `regex` package, not stdlib `re`). Returns `{"requires_content": true}` only for descriptions genuinely outside both lists (semantic/fuzzy judgment, cross-run trends) — not a general "content is unavailable" gate; raw content has been available since the hashing-removal refactor.

**Dashboard** (`dashboard/`) — the UI is served from `dashboard/mission-control.html` (nginx default). No build step. All data fetched from Customer API.

## Database Schema

The schema is defined inline in the service that owns each table:
- `events`, `failure_signals`, `api_keys`, `fixes`, `deploy_events` → `services/ingest/ingest_svc/db/postgres.py`
- `processed_runs`, `issues` → `services/detector/detector_svc/db.py`
- `digest_log` → `services/alerts/alerts_svc/db.py`
- `fixes` is also idempotently created on API startup in `services/api/api_svc/db/queries.py`
- `custom_detectors`, `custom_detector_results` → created by both API (`services/api/api_svc/db/queries.py`) and detector worker (`services/detector/detector_svc/db.py`) with `IF NOT EXISTS`; whichever starts first wins

The `events` table is **partitioned by `received_at`** (monthly range partitions, `events_YYYYMM`). On every ingest startup `ensure_schema()` calls `_ensure_event_partitions()` to create the current + next 3 months of child partitions and an `events_default` safety partition. `prune_old_events(retention_days=90)` drops partitions older than the retention window (instant DDL drop, no vacuum needed) and is run automatically — a background task in `ingest_svc`'s lifespan (`main.py`'s `_prune_loop`) fires it once at startup then daily, configurable via `EVENT_RETENTION_DAYS`. `POST /admin/prune-events` triggers it manually. See `docs/operations.md` for scheduling, monitoring, and the startup staleness check. The PRIMARY KEY is `(id, received_at)` — no other table uses `events.id` as a FK. Existing non-partitioned deployments are unaffected (the `CREATE TABLE IF NOT EXISTS` is a no-op); migration requires an offline `ALTER TABLE … RENAME` + re-insert.

The `fixes` table records every autofix action (clipboard copy or GitHub PR):
```sql
fixes(id, run_id, signal_id, fix_content, fix_type, applied_via,
      langfuse_prompt_name, langfuse_version, applied_at)
```
`langfuse_prompt_name`/`langfuse_version` are historical column names from the
removed Langfuse apply-fix integration — kept as-is rather than migrated.
`langfuse_prompt_name` is always `null` now; `langfuse_version` is reused to
store the GitHub PR number for `applied_via='github_pr'` fixes.

The `custom_detectors` table stores user-defined detectors:
```sql
custom_detectors(id, agent_id, name, description, config_json,
                 status, created_at, total_runs, shadow_fire_count)
-- status: 'shadow' | 'active' | 'paused'
-- shadow_fire_count only incremented when status = 'shadow'
```

The `custom_detector_results` table records per-run evaluation outcomes:
```sql
custom_detector_results(id, detector_id, run_id, agent_id, fired, evaluated_at)
-- ON DELETE CASCADE from custom_detectors
```

## Detectors

All 17 detector classes are in `packages/sdk-py/dunetrace/detectors.py` — 16 in `TIER1_DETECTORS` plus `PromptInjectionDetector` (handled separately). Each returns a `FailureSignal` with an `evidence` dict — the field names vary by detector:

| Detector | Step range fields in evidence |
|---|---|
| `TOOL_LOOP` | `first_step`, `last_step` |
| `LLM_TRUNCATION_LOOP` | `first_truncation_step`, `last_truncation_step` |
| `CONTEXT_BLOAT` | `first_call_step`, `last_call_step` |
| `RETRY_STORM`, `CASCADING_TOOL_FAILURE` | `first_fail_step` only |
| `GOAL_ABANDONMENT` | `last_tool_step`, `current_step` |
| `FIRST_STEP_FAILURE` | `failed_step` only |
| `SLOW_STEP` | `step_index` only |
| `EMPTY_LLM_RESPONSE` | `first_step` only |
| All others | no step range — fall back to `signal.step_index` |

`_get_step_range()` in `explain_common.py` handles this normalization via `_STEP_RANGE_FIELDS`. Always use it; never read evidence step fields directly.

Thresholds are configured in `detectors.yml` (root of repo). Restart the detector container to apply changes. Per-agent-category overrides are supported — the category name must match `agent_id`.

**Custom detectors (JSON-config)** are in `services/detector/detector_svc/custom_detector.py`. `evaluate_custom_detector(config, state, evaluation_budget_ms, regex_timeout_ms)` evaluates a mix of metric-based conditions (12 supported metrics computed from `RunState` fields) and content-based conditions (text inspection via `contains`/`starts_with`/`ends_with`/`equals`/`length_gt`/`length_lt`/`regex_matches` against `tool_args`/`tool_error`/`llm_output`/`input_text`) — see `docs/detectors.md`. All conditions AND together; returns `None` if any fails, or a signal dict if all pass. A per-detector wall-clock budget (default 10ms) aborts evaluation rather than stalling the shared worker loop; `regex_matches` uses the `regex` package's native timeout, not stdlib `re` (ReDoS protection). Signals are written via `write_custom_signal()` in `detector_svc/db.py` which bypasses the `FailureType` enum (custom failure types are stored as raw TEXT). The custom detector block runs after all built-in detectors in `process_run()`, inside a broad `try/except` so a custom detector bug never blocks built-in detection.

**Custom detectors (Python-class)** — `BaseDetector` is publicly exported and importable; `__init_subclass__` auto-registers any subclass defined outside `dunetrace.detectors` itself into `CUSTOM_DETECTOR_REGISTRY`. `detector_svc/custom_python_detectors.py::load_custom_detector_plugins()` imports every `*.py` file from `DUNETRACE_CUSTOM_DETECTORS_PATH` (default `~/.dunetrace/detectors/`) into its own isolated module namespace at worker startup — one malformed file is logged and skipped, never crashes the service. `detector_svc/detectors.py::get_detectors()` merges registered classes into the battery on every call, for every agent category. A plugin signal must set `failure_type=FailureType.CUSTOM` and `evidence["detector_name"] = self.name` — `process_run()` (`worker.py`) checks for both and routes matching signals through `write_custom_signal()` (TEXT failure_type) rather than `write_signals()` (closed-enum, `LIVE_DETECTORS`-gated); `SHADOW_BY_DEFAULT` on the class (default `True`) controls the `shadow` flag. See `docs/detectors.md`'s "Python-class custom detectors" section.

## Root Cause, Fix Classification, and Autofix

Root-cause analysis is **fully native** — `services/api/api_svc/native_explain.py::build_native_explain_prompt(signal, events)` builds the LLM analysis prompt from Dunetrace's own `events` (the same data `get_run_detail()` returns — raw, unhashed). No external tracing system is consulted at any point; `explain_signal` in `services/api/api_svc/routers/signals.py` takes no request body.

**Fix classification** (`services/api/api_svc/fix_classification.py::classify_fix(signal)`) splits every signal into one of two categories — this is the primary axis, not `fix_type`:

- **`dunetrace_native`** — the fix is a runtime guardrail (a `Policy`) Dunetrace can enforce itself, no customer prompt/code change needed. Only `TOOL_LOOP`, `RETRY_STORM`, `CASCADING_TOOL_FAILURE`, and `STEP_COUNT_INFLATION` qualify — their evidence maps unambiguously onto an existing `PolicyCondition` trigger (`tool_call_count` / `error_count` / `step_count`). `build_suggested_policy(signal)` derives the policy deterministically from evidence (no LLM call for the policy shape) and returns it shaped exactly like `routers/policies.py`'s `PolicyCreate` body — the dashboard POSTs it to the existing `POST /v1/policies` unchanged, after a confirmation dialog. `apply_blocked` is always `False` for this category.
- **`customer_code`** — everything else (system prompt wording, tool schema, actual code/infra). Dunetrace has no write access to any of this, so it only ever produces a diff (`fix_content`/`fix_patch`, from `_call_llm`). `fix_type` sub-categorizes the diff: `_CODE_CHANGE_TYPES` (code/infra fix), `_NO_AUTO_APPLY_TYPES` (`PROMPT_INJECTION_SIGNAL`, always blocked), else `prompt_addition`. `apply_blocked` is `False` for `code_change` only when `settings.github_configured` (see below); always `True` for `prompt_addition` (no automated apply path exists) and `no_auto_apply`.

**GitHub PRs for code_change fixes** — `POST /v1/signals/{id}/open-pr` (`services/api/api_svc/github_client.py::create_fix_pr`) opens a draft PR with the fix diff, gated on `GITHUB_TOKEN`/`GITHUB_REPO` in `.env`. This is the only remaining automated apply path — `prompt_addition` fixes (system prompt wording) have no automated apply mechanism at all; Dunetrace can read/analyze a stored system prompt but has no write access back into wherever it actually lives (the customer's own code). `open_pr` carries the same `_NO_AUTO_APPLY_TYPES` guard `apply_fix` used to (403 for `PROMPT_INJECTION_SIGNAL`) since it's now the last endpoint that writes anything on the customer's behalf.

The explain endpoint (`POST /v1/signals/{id}/explain`) returns one of two shapes:
```json
{
  "signal_id": 348,
  "source": "native | signal_only",
  "root_cause": "...",
  "fix_category": "dunetrace_native",
  "suggested_policy": {"name": "...", "agent_id": "...", "condition": {...}, "action": {...}, "priority": 100, "enabled": true},
  "fix_type": "policy",
  "apply_blocked": false
}
```
```json
{
  "signal_id": 349,
  "source": "native | signal_only",
  "root_cause": "...",
  "fix_category": "customer_code",
  "fix_content": "...",
  "fix_patch": "...",
  "fix_type": "prompt_addition | code_change | no_auto_apply",
  "apply_blocked": false
}
```

The SDK's `run.started` payload carries the raw `system_prompt` text passed to `dt.run()` (still also folded into `agent_version`'s hash for grouping) — see `native_explain.py::_extract_system_prompt`'s docstring. This is instrumentation-dependent: callers that omit `system_prompt`, or events ingested before this field existed, still show "(not found in events)" in native explain's "system prompt in use" section.

## Ingest API Endpoints

| Endpoint | Description |
|---|---|
| `POST /v1/ingest` | Accept a batch of agent events from the SDK |
| `POST /v1/otlp/traces` | OTLP/HTTP trace receiver — accepts both `application/json` and `application/x-protobuf` (the default for most real OTel Collectors and `OTLPSpanExporter`), either gzip-compressed (`Content-Encoding: gzip`) or not. Auth via `Authorization: Bearer <key>` (optional in dev mode); rate-limited same as `/v1/ingest`, bucketed by that header (not a body field, since OTLP auth isn't in the JSON body). Agent identity from `service.name` resource attribute; override with `X-Dunetrace-Agent-Id` header — that same header is also what the per-agent rate-limit sub-quota (see `docs/operations.md`) keys on for this endpoint, since decoding the body just to read `service.name` would defeat the point of not decoding it for the auth bucket either; a trace relying on `service.name` alone gets key-level limiting only, no per-agent sub-limit. Returns `{}`. Implemented in `ingest_svc/routers/otlp.py`, mapper in `ingest_svc/otel.py` (`protobuf_to_resource_spans()` converts a parsed `ExportTraceServiceRequest` into the same dict shape the JSON path already produces, so `otlp_to_events()` needs no format-specific branching). Each resourceSpan and each trace is mapped in its own try/except — one malformed one is logged and skipped rather than dropping every other valid trace in the same batch. |
| `POST /v1/deploy` | Record a deploy marker (`agent_id`, `version`, optional `meta` dict). Called by `dt.mark_deploy()`. Writes to `deploy_events` table. Returns `{id, agent_id, version, deployed_at}` |
| `GET /v1/policies` | Fetch runtime policies for an agent (SDK-facing) |
| `POST /v1/keys` | Admin-only (requires `ADMIN_API_KEY` env var to match `admin_key` in the body). Bootstraps the first API key for a fresh self-hosted install — `Customer API`'s own `POST /v1/keys` requires an existing key, so it can't be the very first one. Hidden from OpenAPI docs. |
| `POST /admin/prune-events` | Admin-only, same auth as above. Manually triggers a retention pass — see `docs/operations.md`. Returns `{partitions_dropped, retention_days}`. Hidden from OpenAPI docs. |
| `GET`/`PUT /admin/keys/{key_id}/agents/{agent_id}/quota` | Admin-only, same auth as above (PUT takes `admin_key` in the body; GET takes it as a query param). View/set a per-agent rate-limit sub-quota (fraction of the key's rpm, default 0.20) — see `docs/operations.md`'s Rate limiting section. `key_id` is the numeric key id, never the raw secret key. Hidden from OpenAPI docs. |

## Customer API Endpoints

| Endpoint | Description |
|---|---|
| `POST /v1/signals/{id}/explain` | Fully native root-cause analysis from Dunetrace's own events; returns `fix_category` (`dunetrace_native` + `suggested_policy`, or `customer_code` + `fix_content`/`fix_patch`) |
| `POST /v1/signals/{id}/open-pr` | Opens a draft GitHub PR for a `customer_code`/`code_change` fix, creates it in the fixes table. `dunetrace_native` fixes apply via `POST /v1/policies` instead — no separate endpoint. `prompt_addition` fixes have no apply endpoint at all — copy manually |
| `POST /v1/signals/{id}/record-copy` | Record clipboard-path fix in fixes table (hidden from OpenAPI docs) |
| `GET /v1/signals/{id}/fix-status` | Check whether a fix reduced recurrence: verdict is `verified / likely_fixed / still_occurring / insufficient_data` |
| `POST /v1/custom-detectors/preview` | Translate plain-English description to structured config via LLM |
| `GET /v1/custom-detectors` | List all custom detectors (optional `?agent_id=` filter) |
| `POST /v1/custom-detectors` | Create a new custom detector (always starts in shadow mode; 201) |
| `GET /v1/custom-detectors/{id}` | Get one custom detector |
| `GET /v1/custom-detectors/{id}/shadow-stats` | Fire rate + sample runs for a shadow detector |
| `PATCH /v1/custom-detectors/{id}` | Update status: `shadow` / `active` / `paused` |
| `DELETE /v1/custom-detectors/{id}` | Delete a custom detector (204) |

**Run detail `include_shadow`** — `GET /v1/runs/{run_id}?include_shadow=true` returns shadow signals (including custom detector signals) alongside live signals. Each signal includes a `shadow: bool` field. Default is `false` — shadow signals are hidden in the normal run view.

## Dashboard

`dashboard/mission-control.html` is the UI entry point (nginx serves it as the default). Vanilla JS, no build step. The run-detail Analysis tab's autofix flow is driven by `explainSignal()` (native root-cause analysis, calls `POST /v1/signals/{id}/explain` — no Langfuse involved) and `openPROnGitHub()` (calls `POST /v1/signals/{id}/open-pr` for `code_change` fixes only, gated on `github_configured`). `_explainSignalId`/`_explainLastData` module-level vars track the current signal's explain result between the two calls.

`apiPost(path, body)` is the POST helper alongside the existing `apiFetch`. `cdPatch(id, body)` and `cdDelete(id)` are helpers for custom detector PATCH/DELETE (separate from `apiPost` to carry the right HTTP method).

Custom detector UI state in `page-config`:
- `openCustomDetectorForm()` / `closeCustomDetectorForm()` — show/hide the new detector form
- `previewCustomDetector()` — calls `/v1/custom-detectors/preview`, renders config
- `saveCustomDetector()` — calls `POST /v1/custom-detectors`, reloads list
- `loadCustomDetectors()` / `renderCustomDetectorCard()` — list + card render
- `activateCustomDetector(id)` / `pauseCustomDetector(id)` / `resumeCustomDetector(id)` / `deleteCustomDetector(id, name)` — lifecycle actions
- Delete button uses `data-cd-id` / `data-cd-name` attributes (not inline JS strings) to avoid XSS via `esc()`

## Testing Native Explain

All tests in `services/api/tests/test_native_explain.py` and `test_signals_explain.py` run without DB, network, or credentials.

The smoke test script `scripts/test_autofix.py` hits the running stack and exercises explain, record-copy, fix-status, and (with `--open-pr`) open-pr against a real signal. Run it after rebuilding the API container: `python scripts/test_autofix.py --agent-id my-agent --signal-id 42`.

## MCP Server

`packages/mcp-server/` — exposes Dunetrace signals to Claude Code, Cursor, and Codex via the Model Context Protocol.

```bash
# Install
cd packages/mcp-server && pip install -e .

# Run (stdio, used by Claude Code and Cursor)
dunetrace-mcp

# Config env vars
DUNETRACE_API_URL=http://localhost:8002   # Customer API base URL
DUNETRACE_API_KEY=dt_dev_test            # Bearer token
```

Tools exposed: `list_agents`, `get_agent_signals`, `get_agent_health`, `get_run_detail`, `get_agent_runs`, `search_signals` (alias: `list_all_signals`), `get_signal_detail`, `get_agent_patterns`, `summarize_agent`, `get_instrumentation_guide`.

**Claude Code** — registered automatically in `~/.claude.json` under key `"dunetrace"`. Restart Claude Code to pick it up.

**Cursor** — add to `.cursor/mcp.json` in your project:
```json
{
  "mcpServers": {
    "dunetrace": {
      "command": "dunetrace-mcp",
      "env": {
        "DUNETRACE_API_URL": "http://localhost:8002",
        "DUNETRACE_API_KEY": "dt_dev_test"
      }
    }
  }
}
```

**Codex / OpenAI Responses API** — run the server with SSE transport and point the tool endpoint at it:
```bash
dunetrace-mcp --sse              # listens on :8000 by default
dunetrace-mcp --sse --port 9000  # custom port
```
